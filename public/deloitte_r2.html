File Polling & High-Volume Data Processing (10:11:49)

4. In your project, how do you know when new files have arrived, and how are you picking up those files for processing? (10:11:49)

There are two primary patterns used to detect and pick up incoming files:

  • Scheduled Polling (Pull Mechanism): A scheduled task (using Spring @Scheduled(cron = "0 0/5 * * * ?") or Quartz Scheduler) periodically scans a designated landing directory (local SFTP folder, NFS mount, or AWS S3 bucket) for incoming files matching specific naming conventions or extensions.
  • Event-Driven Notifications (Push Mechanism): Utilizing file system watchers (like Java WatchService) or cloud storage event notifications (e.g., S3 Event Notifications publishing to an SQS queue or Kafka topic) that trigger processing immediately upon file arrival.

Once picked up, files are moved from the landing/inbox directory to a staging/processing directory to prevent concurrent pollers from picking up the same file while it is actively being read.

5. If you are hitting the system every 5 minutes to poll for files, how do you handle duplicate files? Let's say a duplicate file arrives, what is your handling strategy? (10:12:20)

Handling duplicate files requires a robust deduplication and idempotency strategy across multiple layers:

  1. Checksum / Hashing (Content Verification): When a file is read, we generate a cryptographic hash (SHA-256 or MD5) of the file content. We check this hash against a database table or Redis cache of previously processed file hashes. If the hash already exists, the file is identified as a duplicate.
  2. Metadata Tracking Table: We maintain a database table (e.g., file_processing_log) storing file metadata: file_name, file_size, received_timestamp, checksum, and status (PROCESSING, COMPLETED, FAILED). Before processing starts, we query this table. If a file with identical metadata is already COMPLETED or PROCESSING, it is skipped.
  3. File Move / Archive Strategy: Successfully processed files are immediately moved to an archive/processed folder with a timestamped suffix, while detected duplicates are moved to a duplicates/rejected folder and an alert is logged.
  4. Database Idempotency: At the record level, downstream database insertions use unique constraints and UPSERT operations (e.g., INSERT ... ON DUPLICATE KEY UPDATE or JPA save() with business keys) so that even if a record is re-processed, it does not create duplicate entries in the database.
6. You mentioned there are millions of records or files coming in, representing a huge volume. Can you explain how you process this high volume rapidly and efficiently? (10:13:04)

To process millions of records with high throughput and low latency, we employ several performance optimization strategies:

  • Chunk-Oriented / Batch Processing: Instead of loading and processing the entire file into memory or inserting records one-by-one, we read and write data in chunks (e.g., batch sizes of 1,000 to 5,000 records). This dramatically reduces database network roundtrips and memory overhead.
  • Multi-Threading & Parallel Processing: We utilize Java ExecutorService (custom thread pools) or Spring Batch partitioners to split large files into smaller partitions and process them concurrently across multiple threads or worker nodes.
  • Streaming APIs: We use memory-efficient streaming readers (like BufferedReader, StAX for XML, or FastCSV) rather than DOM parsers or holding full file contents in RAM, preventing OutOfMemoryError.
  • JDBC Batching & Hibernate Optimization: In the persistence layer, we enable JDBC batching (spring.jpa.properties.hibernate.jdbc.batch_size=50, order_inserts=true) and disable second-level caching during bulk operations to maximize write speeds.
  • Asynchronous Decoupling via Message Brokers: Once file records are read, they can be published as events to Apache Kafka or RabbitMQ topics, allowing multiple independent consumer services to process and persist the records horizontally at scale.
7. Are you working on batch processing, specifically Spring Batch? Can you explain its architecture and core components? (10:14:07)

Yes, Spring Batch is the robust framework we use for processing large volumes of data reliably. Its architecture revolves around several key components:

  • Job: Represents the entire batch process executed from start to finish. A Job is composed of one or more Steps.
  • Step: An independent phase of a Job. Most high-volume processing uses Chunk-Oriented Processing within a Step, which consists of three interfaces:
    • ItemReader: Reads data one item at a time from a data source (e.g., FlatFileItemReader for CSVs or JdbcCursorItemReader for databases).
    • ItemProcessor: Applies business validation, data transformation, or filtering on each item read. Returning null filters out the item from being written.
    • ItemWriter: Receives a list (chunk) of processed items and writes them in bulk to the destination (e.g., JdbcBatchItemWriter or JpaItemWriter).
  • JobRepository: The persistence mechanism that stores Job and Step execution metadata, status, start/end times, and read/write commit counts in database tables (e.g., BATCH_JOB_EXECUTION). This enables restartability from the exact point of failure.
  • JobLauncher: The interface responsible for launching a Job with a given set of JobParameters.

Java Core: Generics & Serialization (10:17:02)

8. What are Generics in Java, and why do we use them? (10:17:02)

Generics (introduced in Java 5) enable types (classes, interfaces, and methods) to operate on objects of various types while providing compile-time type safety.

Key Benefits:

  • Compile-Time Type Safety: The compiler catches type mismatch errors at compile time rather than failing at runtime with a ClassCastException.
  • Elimination of Manual Type Casting: When retrieving elements from a generic collection (e.g., List<String>), explicit casting is no longer required.
  • Code Reusability: Allows writing generic algorithms and data structures that work seamlessly across different data types (e.g., Java Collections Framework).
9. What is the difference between Upper Bounded and Lower Bounded wildcards in Java Generics? (10:17:49)

Bounded wildcards restrict the types that can be used as type arguments in generic structures. They follow the PECS Principle (Producer Extends, Consumer Super):

  • Upper Bounded Wildcards (<? extends T>): Restricts the unknown type to be a specific type T or any of its subclasses.
    • Usage (Producer Extends): Used when you only want to read (produce) data from a collection. For example, a method accepting List<? extends Number> can safely read integers or doubles as Number objects, but you cannot add new elements to it (except null) because the exact subtype is unknown at compile time.
  • Lower Bounded Wildcards (<? super T>): Restricts the unknown type to be a specific type T or any of its superclasses (up to Object).
    • Usage (Consumer Super): Used when you want to write (consume) or insert elements into a collection. For example, a method accepting List<? super Integer> allows you to safely insert Integer objects into a list of integers, numbers, or objects.
10. Have you worked on Serialization? What are the different ways to achieve serialization in Java? (10:18:23)

Serialization is the mechanism of converting an object's state into a stream of bytes so that it can be persisted to a file/database or transmitted over a network. The reverse process of reconstructing the object from the byte stream is called Deserialization.

Ways to achieve Serialization in Java:

  1. Implementing the java.io.Serializable Interface: This is a marker interface (contains no methods). When a class implements Serializable, Java's default serialization mechanism (via ObjectOutputStream and ObjectInputStream) automatically serializes its fields.
    • transient keyword: Used on fields that should be skipped during serialization (e.g., passwords or temporary caches).
    • serialVersionUID: A unique version identifier used during deserialization to verify that the sender and receiver have compatible class definitions.
  2. Implementing the java.io.Externalizable Interface: This interface extends Serializable and provides complete custom control over the serialization process by requiring implementation of two methods: writeExternal(ObjectOutput out) and readExternal(ObjectInput in). This is faster and more memory-efficient than default serialization because you explicitly specify which fields to serialize.
  3. Modern JSON / XML Serialization (Library-Based): In contemporary microservices and REST architectures, binary Java serialization is rarely used due to cross-language incompatibility and security vulnerabilities. Instead, objects are serialized into JSON or XML using libraries like Jackson (ObjectMapper), Gson, or JAXB.

OOPs & Exception Handling (10:19:45)

11. Let's say Class A has a public method, and Class B extends Class A. Can we override that method in Class B and change its access modifier to default (package-private)? (10:19:45)

No, we cannot. This violates Java's method overriding rules and the Liskov Substitution Principle.

Rule: When overriding a method in a subclass, you cannot assign a more restrictive (weaker) access modifier than the access modifier of the overridden method in the superclass. You can only assign an equal or less restrictive (wider) access modifier.

  • Visibility hierarchy (from most restrictive to least restrictive): private → default (package-private) → protected → public.
  • Since the method in Class A is public (the widest visibility), the overriding method in Class B must remain public. Attempting to change it to default, protected, or private will result in a compile-time error: "attempting to assign weaker access privileges; was public".

13. What is the topmost (root) class of the Exception handling hierarchy in Java? (10:21:14)

The topmost root class of the Java exception hierarchy is java.lang.Throwable, which is a direct subclass of Object.

Throwable has two primary subclasses:

  • Exception: Represents exceptional conditions that a reasonable application should try to catch and recover from (contains both Checked and Runtime exceptions).
  • Error: Represents severe problems that occur within the JVM environment itself, which an application should generally not attempt to catch or handle (e.g., OutOfMemoryError, StackOverflowError, VirtualMachineError).
14. In a method with a try-catch-finally block where the function does NOT throw any exception: from try you return 1, from catch you return 2, and from finally you return 3. What will be the output of the function? (10:21:55)

The output (return value) of the function will be 3.

Explanation: In Java, the finally block is guaranteed to execute whether an exception occurs or not (except in extreme cases like System.exit(0), JVM crash, or fatal hardware failure). When a return statement is encountered inside the try block, the return expression is evaluated, but the actual return to the caller is deferred until the finally block executes.

Because the finally block also contains an explicit return statement (return 3;), this statement overrides any value previously scheduled to be returned from the try (or catch) block.

public class ExceptionReturnExample {
    @SuppressWarnings("finally")
    public static int testMethod() {
        try {
            return 1;
        } catch (Exception e) {
            return 2;
        } finally {
            return 3; // This return overrides the return 1 from the try block!
        }
    }

    public static void main(String[] args) {
        System.out.println("Result: " + testMethod()); // Output: Result: 3
    }
}

Java Collections & Concurrency (10:22:42)

15. What is the difference between Fail-Fast and Fail-Safe iterators in collections? In the case of Fail-Fast, why does Java throw an exception? (10:22:42 - 10:23:43)
  • Fail-Fast Iterators: Operate directly on the original collection's underlying data structure. If the collection is structurally modified (elements added or removed) after the iterator is created—by any thread, or even by the same thread without using the iterator's own remove() method—the iterator immediately throws a ConcurrentModificationException.
    • Examples: Iterators of standard collections like ArrayList, HashMap, HashSet.
  • Fail-Safe (Non-Fail-Fast / Weakly Consistent) Iterators: Do not throw ConcurrentModificationException if the collection is modified during iteration. They either iterate over a clone/copy of the collection or use weakly consistent data structures that tolerate concurrent modifications.
    • Examples: Iterators of concurrent collections like CopyOnWriteArrayList, ConcurrentHashMap.

Why does Fail-Fast throw an exception? (Internal Mechanism):

Standard collections maintain an internal structural modification counter named modCount. When an iterator is instantiated, it captures the current value of modCount in a local variable named expectedModCount.

During every iteration step (when calling hasNext() or next()), the iterator calls an internal method checkForComodification() which compares modCount against expectedModCount. If another thread (or direct collection calls) modified the collection structure, modCount increments while expectedModCount remains unchanged. The mismatch indicates that the underlying data has changed unpredictably, triggering a ConcurrentModificationException to prevent arbitrary behavior, silent data corruption, or infinite loops.

16. When multiple threads are accessing and modifying a list concurrently, why shouldn't we use standard ArrayList, and how does CopyOnWriteArrayList resolve thread-safety issues? (10:24:44)

Why standard ArrayList fails in multi-threaded environments: ArrayList is not synchronized. If one thread iterates over the list while another thread adds or removes elements, race conditions occur, leading to data corruption, indexing errors, or ConcurrentModificationException.

How CopyOnWriteArrayList solves this:

  • Copy-On-Write Mechanism: All mutative operations (like add, set, remove) are implemented by making a fresh, independent copy of the underlying array using internal locks (like ReentrantLock). The modification is applied to the copy, and once complete, the internal array reference is atomically updated to point to the new array.
  • Lock-Free Reads: Read operations (like get, iterator) do not require locking. They operate on a immutable snapshot of the array that existed at the exact moment the read or iterator was initiated.
  • When to use: Ideal for read-heavy, write-infrequent scenarios (such as listener lists, routing tables, or configuration caches). Since cloning the array on every write operation is memory- and CPU-intensive, it should be avoided in write-heavy workloads.
17. What is the contract between hashCode() and equals() methods? What happens if you override only hashCode() (or only equals()) in hashing collections like HashMap or HashSet? (10:25:08 - 10:25:41)

The Contract between hashCode() and equals():

  1. If two objects are equal according to the equals(Object) method, calling hashCode() on both objects must produce the exact same integer result.
  2. If two objects have the same hashCode(), they are not necessarily equal according to equals() (this is known as a hash collision).
  3. Whenever hashCode() is invoked on the same object more than once during an execution of a Java application, it must consistently return the same integer, provided no information used in equals comparisons on the object is modified.

What happens if you override ONLY hashCode() (and NOT equals())?

When you insert two logically identical objects (e.g., two Employee objects with the same ID) into a HashSet or HashMap, they will generate the exact same hash code and land in the same bucket. However, when the hash map checks for duplicate keys in that bucket, it calls equals(). Since equals() was not overridden, it defaults to Object.equals(), which compares memory references (==). Because the two instances have different memory addresses, equals() returns false. As a result, the map/set treats them as distinct keys, leading to duplicate entries in a HashSet or multiple keys with identical logical values in a HashMap!

What happens if you override ONLY equals() (and NOT hashCode())?

Two logically equal objects will be considered equal by equals(), but because hashCode() defaults to Object.hashCode() (often derived from memory address), they will generate completely different hash codes and land in completely different buckets in the hash table. Therefore, when you attempt to retrieve a value using map.get(new Employee(100)), the hash map checks the wrong bucket and returns null, failing to find the entry even though an equal key exists!

18. Explain the internal working of HashSet and how it removes or prevents duplicate values. (10:26:17 - 10:26:49)

Internal Working: Internally, a HashSet is backed entirely by a HashMap instance:

private transient HashMap<E,Object> map;
private static final Object PRESENT = new Object(); // Dummy value

When you add an element to a HashSet, the set inserts the element as the key into the internal HashMap, while passing a constant, static dummy object named PRESENT as the value for all entries.

How it prevents duplicate values:

When you invoke hashSet.add(element), it executes map.put(element, PRESENT) internally. The HashMap.put() method performs the following checks:

  1. It computes the hash code of element to find the target bucket index in the hash table array.
  2. If the bucket is empty, a new node is created, and put() returns null. The HashSet.add() method sees that the return value is null, confirms that the element was not present, and returns true.
  3. If the bucket already contains elements (collision), it traverses the linked list or red-black tree at that bucket index and compares the incoming element with existing keys using: (e.hash == hash && ((k = e.key) == element || (element != null && element.equals(k))))
  4. If an existing key matches the incoming element, the HashMap replaces the old value with PRESENT and returns the old value (which is PRESENT).
  5. Because map.put() returned an existing object (not null), HashSet.add() knows that the element is a duplicate and returns false without adding a new entry to the set!

Java 8 Functional Interfaces (10:27:13)

19. What is a Functional Interface in Java 8? Can one Functional Interface extend another Functional Interface? (10:27:13 - 10:27:36)

A Functional Interface is an interface that declares exactly one abstract method (known as the Single Abstract Method or SAM). It serves as the target type for Lambda expressions and Method References. It is annotated with @FunctionalInterface (optional, but recommended for compiler enforcement).

Note: A functional interface can contain any number of default methods, static methods, or public method overrides from the java.lang.Object class (such as toString, equals, hashCode).

Can a Functional Interface extend another Functional Interface?

Yes, but whether the child interface remains a valid Functional Interface depends on how methods are declared:

  • Case 1 (Remains a Functional Interface): If Child Interface B extends Parent Functional Interface A and does not declare any new abstract method (or simply overrides Parent A's abstract method with the exact same signature), Interface B inherits exactly one abstract method from A and is a valid Functional Interface.
  • Case 2 (No longer a Functional Interface): If Child Interface B extends Parent Functional Interface A and declares a new, distinct abstract method, Interface B now possesses two abstract methods. Consequently, Interface B is no longer a functional interface. If you annotate Interface B with @FunctionalInterface in this scenario, the compiler will trigger an error: "Multiple non-overriding abstract methods found in interface B".

JPA / Hibernate & Database Persistence (10:28:09)

20. Which ORM framework are you using? What is a Criteria Query in JPA / Hibernate? (10:28:09)

We use Hibernate / JPA (Java Persistence API) implemented via Spring Data JPA.

Criteria Query (JPA Criteria API): A programmatic, type-safe API used to construct database queries using Java objects at runtime without writing raw SQL or static JPQL/HQL strings.

Why we use Criteria Queries: They are exceptionally powerful for building dynamic queries where search filters, sorting, and joins change at runtime based on optional user inputs (e.g., advanced search screens with multiple optional filter criteria). Since queries are built using Java types and metamodels, syntax errors and type mismatches are caught at compile time, and SQL injection vulnerabilities are eliminated.

Core Components:

  • CriteriaBuilder: Factory interface used to construct query elements, expressions, predicates, ordering, and grouping.
  • CriteriaQuery<T>: Represents the overall query structure (SELECT, FROM, WHERE, ORDER BY clauses) and return type.
  • Root<T>: Represents the root entity in the FROM clause, providing access to entity attributes and joins.
21. Between JPQL/HQL, Native SQL, and Criteria Queries, which one is fastest in execution speed, and why? (10:28:41)

In terms of runtime query execution speed, the ranking is:

  1. Fastest — Native SQL (@Query(nativeQuery = true)): Native SQL executes the fastest because it completely bypasses the ORM query translation layer. The SQL query string is passed directly to the underlying JDBC driver and database engine without modification. Furthermore, it allows developers to utilize database-specific vendor optimizations, query hints, and complex indexing features that JPA syntax might not support.
  2. Second Fastest — JPQL / HQL (@Query): JPQL and HQL are object-oriented query languages that operate on entity classes rather than database tables. During initial startup or first execution, the Hibernate query parser must translate the JPQL/HQL string into vendor-specific SQL. However, Hibernate caches this compiled SQL query execution plan in its AST (Abstract Syntax Tree) cache, making subsequent executions very fast and comparable to Native SQL.
  3. Slowest — Criteria Query (JPA Criteria API): Criteria queries have the highest computational overhead during query construction. Because the query is constructed dynamically as an object tree at runtime, Hibernate must evaluate the object graph, validate types, and generate the equivalent SQL query string on the fly every time the query is built.

Summary Best Practice: Use Native SQL or JPQL for static, performance-critical queries. Reserve Criteria Queries (or Spring Data JPA Specifications) for complex, dynamic queries where runtime flexibility and compile-time type safety outweigh the minor SQL generation overhead.

22. What are the different strategies available to create a primary key in JPA / Hibernate (@GeneratedValue)? (10:29:05)

In JPA, the @GeneratedValue(strategy = GenerationType.XXX) annotation specifies how primary key values are generated. There are four primary strategies:

  • GenerationType.IDENTITY: Relies on an auto-incremented database column (e.g., AUTO_INCREMENT in MySQL/H2 or BIGSERIAL in PostgreSQL). The database generates the primary key value upon record insertion.
    • Important Performance Note: Using IDENTITY disables Hibernate's JDBC batch insert optimization (hibernate.jdbc.batch_size) because Hibernate must execute the INSERT statement immediately to obtain the generated ID before the transaction commits.
  • GenerationType.SEQUENCE: Uses a dedicated database sequence object to generate IDs (supported natively by PostgreSQL, Oracle, and modern SQL Server). Highly efficient and fully supports JDBC batch inserts because Hibernate can pre-fetch a block of sequence IDs in memory using sequence allocation sizes (pooled / HiLo optimizer) before executing batch inserts.
  • GenerationType.TABLE: Uses a separate database table (typically named hibernate_sequences) to simulate a sequence by generating and storing the next primary key value. While database-agnostic and portable across all relational DBs, it is the slowest strategy due to row-level locking and extra database queries required to update the ID table.
  • GenerationType.AUTO (Default): Lets the persistence provider (Hibernate) select the most appropriate generation strategy based on the configured database dialect. In modern Hibernate versions (5+), this typically defaults to SEQUENCE for PostgreSQL/Oracle and IDENTITY/TABLE for MySQL depending on configuration.

Bonus Mention: For distributed architectures and microservices, we also use UUID primary key generation (@GeneratedValue(strategy = GenerationType.UUID)) to generate globally unique identifiers without requiring network roundtrips to the database.

23. In Hibernate or JPA, if you need to execute a dynamic query that performs a JOIN between two tables based on an optional keyword passed from an API, how do you implement this? (10:30:09)

The cleanest and most scalable way to implement dynamic queries with conditional joins in Spring Boot is using Spring Data JPA Specifications (Specification<T>), which is built on top of the JPA Criteria API.

Implementation Steps:

  1. Ensure your repository extends JpaSpecificationExecutor<Entity> alongside JpaRepository<Entity, Long>.
  2. Create a custom static Specification method that checks whether the API keyword parameter is present.
  3. If the keyword is present, dynamically instantiate a Join using root.join("associatedEntity", JoinType.LEFT) and construct the filtering predicate using CriteriaBuilder.

Code Example:

Suppose we have an Order entity associated with a Customer entity, and we want to dynamically join and filter by Customer Name only if the API passes a search keyword:

import org.springframework.data.jpa.domain.Specification;
import jakarta.persistence.criteria.Join;
import jakarta.persistence.criteria.JoinType;
import jakarta.persistence.criteria.Predicate;
import java.util.ArrayList;
import java.util.List;

public class OrderSpecifications {

    public static Specification<Order> getOrdersByDynamicFilter(String keyword) {
        return (root, query, cb) -> {
            List<Predicate> predicates = new ArrayList<>();
            
            // Default condition: fetch only active orders
            predicates.add(cb.equal(root.get("status"), "ACTIVE"));

            // Dynamically add JOIN and condition ONLY if keyword is passed from API
            if (keyword != null && !keyword.trim().isEmpty()) {
                // Perform a Left Outer Join between Order and Customer tables
                Join<Order, Customer> customerJoin = root.join("customer", JoinType.LEFT);
                
                // Add case-insensitive LIKE condition on customer's name
                Predicate customerNamePredicate = cb.like(
                    cb.lower(customerJoin.get("name")), 
                    "%" + keyword.trim().toLowerCase() + "%"
                );
                predicates.add(customerNamePredicate);
            }

            // Combine all predicates with AND operator
            return cb.and(predicates.toArray(new Predicate[0]));
        };
    }
}

In the Service layer, you simply invoke: orderRepository.findAll(OrderSpecifications.getOrdersByDynamicFilter(keyword));. If keyword is null or empty, the JOIN is omitted, optimizing query execution!
