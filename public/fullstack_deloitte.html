System Architecture: Telecom Billing (16:06:18)

2. You mentioned building a telecom billing platform handling 20+ MVNOs and 100M+ Call Detail Records (CDRs) daily. Can you walk me through the end-to-end architecture from CDR ingestion to billing output?

Senior Dev Answer:

The architecture is designed for high throughput, fault tolerance, and eventual consistency:

  • Ingestion Layer: Network elements push CDRs via SFTP. We use Apache NiFi or a custom Go/Java service to ingest and validate the raw files, pushing individual records onto an Apache Kafka topic partitioned by MVNO ID.
  • Stream Processing & Deduplication: Apache Flink consumes the Kafka streams. It performs real-time deduplication (using state backends) and standardizes the CDR formats.
  • Rating Engine: A microservice built with Spring Boot and a rule engine (like Drools) consumes the standardized CDRs. It applies complex tariff plans and discounts in memory for low latency.
  • Storage: Processed records are persisted into a NoSQL database (like Apache Cassandra) for high write-throughput storage and fast retrieval.
  • Billing & Invoicing: A batch processing system (Spring Batch) runs at the end of the billing cycle, aggregating data from Cassandra, generating invoices, and storing the final financial records in a relational database like PostgreSQL for ACID compliance.

System Design: Data Integrity (16:10:30)

3. In telecom billing, duplicate or lost CDRs directly impact revenue. How do you design safeguards against these issues?

Senior Dev Answer:

  • Duplicates: Every CDR must have a globally unique identifier generated at the source. At the ingestion layer, we implement deduplication using Bloom Filters combined with Redis for a sliding window of recent IDs. The database also enforces uniqueness constraints on this ID.
  • Lost Records: We implement an "Exactly-Once" processing semantic where possible using Kafka transactional producers. Furthermore, we use end-to-end reconciliation: the ingestion layer logs the count of records received per batch, and the rating engine logs the count processed. An independent reconciliation service periodically compares these counts and alerts on discrepancies.
  • Orphan Records: Records that fail validation or rating are sent to a Dead Letter Queue (DLQ). These are monitored and can be manually corrected or automatically replayed.

React: Rendering & Optimization (16:14:03)

4. What causes a React component to re-render, and how do you prevent unnecessary rendering? How would you optimize a page with an interactive map and multiple API-driven widgets?

Senior Dev Answer:

  • Causes of Re-renders: State changes (useState, useReducer), Prop changes, Parent component re-rendering, or changes in Context values.
  • Prevention: I use React.memo for component-level memoization, and useMemo / useCallback to preserve object references across renders. Context is split granularly to prevent unrelated components from updating.
  • Map & Widget Optimization: For heavy interactive pages, I lazy load the map component using React.lazy(). For the map events (like panning), I heavily debounce the event handlers to avoid spamming state updates. The API-driven widgets are decoupled; they manage their own data fetching using libraries like React Query, which handles caching and prevents redundant network requests.

React: Async Data Management (16:15:10)

5. How would you manage loading asynchronous data (weather, traffic, map data) at different times, handling errors, and managing stale states in the UI?

Senior Dev Answer:

I rely on a robust data-fetching library like React Query (TanStack Query) or SWR.

  • Loading States: These libraries provide isLoading and isFetching flags. I use these to render skeleton loaders for individual widgets so the rest of the page remains interactive.
  • Error Handling: I use the isError flag for local widget fallbacks (e.g., "Failed to load weather"). For critical errors, I wrap the component tree in a React Error Boundary to prevent the entire app from crashing.
  • Stale Data: I configure an appropriate staleTime for each data source (e.g., weather might be stale after 15 minutes, traffic after 2 minutes). React Query automatically refetches data in the background when the user refocuses the window or the data becomes stale, providing a seamless experience.

Frontend Security & Accessibility (16:17:57)

6. How do you build a secure front-end application consuming a JWT-protected API? What accessibility practices would you apply to a dashboard UI?

Senior Dev Answer:

  • JWT Security: I never store JWTs in localStorage or sessionStorage due to XSS vulnerability. Instead, I architect the backend to return the JWT inside an HttpOnly, Secure cookie. For protection against CSRF, I use anti-CSRF tokens or ensure SameSite=Strict attributes on the cookie.
  • Accessibility (a11y): Dashboards must be navigable. I ensure proper semantic HTML (using <nav>, <main>, <section>). Interactive elements like charts or custom dropdowns use proper ARIA roles and attributes (aria-expanded, aria-live for dynamic data updates). I also ensure a high color contrast ratio and full keyboard navigability (managing focus states).

Spring Boot: Dependency Injection & API Design (16:21:01)

7. Can you explain Spring Boot dependency injection? How would you design a REST API for a subscriber activation?

Senior Dev Answer:

  • Dependency Injection (DI): It's an implementation of Inversion of Control. Instead of objects creating their dependencies, the Spring IoC Container injects them. As a senior developer, I strictly use Constructor Injection over field injection (@Autowired) because it makes dependencies explicit, allows fields to be final (immutable), and simplifies unit testing without requiring the Spring context.
  • API Design (Subscriber Activation): I would design an idempotent POST endpoint: POST /api/v1/subscribers/{id}/activations. It returns a 202 Accepted if the activation is an asynchronous process (putting a message on a queue) along with a Location header pointing to a status endpoint. I would use standard HTTP status codes, correlation IDs for tracing, and robust payload validation.

Java: Exception Handling & Memory Leaks (16:25:17 & 16:32:54)

8. How do you structure exception handling in a Spring Boot API? What are common causes of memory leaks in Java backend services?

Senior Dev Answer:

  • Exception Handling: I use @RestControllerAdvice for global exception handling. I map custom business exceptions and standard exceptions (like validation errors) to a standardized JSON response format, usually following the RFC 7807 Problem Details specification. This ensures clients always receive a predictable error structure.
  • Memory Leaks: Common causes include: Unclosed resources (database connections, streams), static collections (like HashMaps) that grow indefinitely as caches without eviction policies, un-removed ThreadLocal variables (especially dangerous in application servers with thread pools), and adding objects to HashSets/HashMaps without properly overriding equals() and hashCode(), causing duplicate entries.

Database: Indexing Trade-offs & Performance (16:27:05)

9. A billing query on a large CDR table is running slow. How do you diagnose it? What are the indexing trade-offs for a table receiving millions of records per day?

Senior Dev Answer:

  • Diagnosis: I start by running an EXPLAIN ANALYZE (in PostgreSQL) or equivalent to inspect the query execution plan. I look for full table scans, high-cost joins, or situations where the database planner is ignoring an index.
  • Indexing Trade-offs: Indexes drastically speed up read queries by allowing O(log N) lookups instead of O(N) scans. However, for a table receiving millions of inserts daily, every new index adds overhead to write operations because the index tree must be updated. It also consumes disk space. In heavy write scenarios, I might prefer table partitioning (e.g., by date) over adding multiple secondary indexes, or delay index creation during bulk data loads.

Coding Assessment: Two Sum (16:39:28)

11. Write a program which takes an array of integers and a target, and returns the indices of two numbers that add up to that target.

Senior Dev Answer:

Instead of a brute-force O(N^2) approach, we can optimize this to O(N) time and O(N) space using a HashMap to store the complements.

class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> map = new HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int complement = target - nums[i];
            if (map.containsKey(complement)) {
                return new int[] { map.get(complement), i };
            }
            map.put(nums[i], i);
        }
        throw new IllegalArgumentException("No two sum solution");
    }
}
